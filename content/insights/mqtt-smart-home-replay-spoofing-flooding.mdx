MQTT is a lightweight publish/subscribe messaging protocol widely used in connected-device systems. Its architecture is convenient: a publisher sends a message to a broker, and subscribers receive messages for topics they are authorised to access. That simplicity also makes it important to understand the security controls surrounding message publication and delivery.

In a smart-home environment, sensor readings may influence dashboards, alerts or automated decisions. A message that arrives at the wrong time, comes from the wrong source or overwhelms a component can have consequences beyond the broker itself. Three useful attack categories for experimental study are replay, spoofing and flooding.

**Replay** involves resending a message that was previously valid. A repeated sensor reading may appear plausible because its contents once represented a genuine observation. Without suitable freshness checks, sequence handling or replay defences, a consumer might process the old information as if it were current. Authentication alone does not necessarily prevent replay of a legitimately authenticated message.

**Spoofing** occurs when a message or source is presented as something it is not. In an MQTT setting, the exact attack depends on broker authentication, topic permissions, transport security and application design. A system that accepts a message simply because it arrived on a familiar topic may be vulnerable to misleading data if an attacker gains publishing access. Topic names are not, by themselves, evidence of source authenticity.

**Flooding** aims to overwhelm a component or communication path with more traffic than it can comfortably handle. In a connected smart-home workflow, the effect may appear as delayed processing, queue growth, message loss or reduced responsiveness. Whether that happens depends on broker configuration, network capacity, subscriber behaviour and application-level processing.

These attack types should not be evaluated only by checking whether a packet was transmitted. A meaningful experiment follows what happened across the system. Did the broker accept the message? Did the intended consumer receive it? Was it rejected by a control? Did the application update its state? Was the result delayed? Did legitimate sensor traffic continue to be processed?

That is why network evidence matters. Packet captures can reveal timing and traffic patterns; broker logs can show access-control decisions; application logs can show whether a reading was accepted or acted upon. Each source has limits. A packet visible on one interface does not automatically prove that a downstream application processed it correctly. Combining evidence from multiple points gives a more defensible picture.

In my doctoral work, I use controlled attack scenarios to investigate encrypted smart-home messaging and system behaviour. The aim is not to claim that any one mechanism makes a smart home secure. It is to understand which properties hold, where controls fail and how to document the results in a way that another researcher can inspect.

<Notes title="Research notes">

**Quality of service is not security.** MQTT's QoS levels 0, 1 and 2 control delivery guarantees. They say nothing about whether a message is authentic or fresh.

**Transport encryption has limits.** TLS between clients and the broker protects messages in transit, but an authorised client, or an attacker holding valid credentials, can still publish misleading or replayed data. Freshness and source checks belong in the application as well.

**Broker access control.** Mosquitto can restrict which users may publish or subscribe to which topics. That narrows what a compromised or rogue client can do, but it depends on credentials being managed well.

**What is deliberately left out.** Attack scripts, broker configuration and addresses from my research environment are not published here.

</Notes>
