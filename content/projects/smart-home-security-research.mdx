## The problem

Smart-home sensors report on temperature, movement, doors and energy use many times a minute. Individually the readings look harmless. Collected over weeks they show when a household is at home, asleep or away. Most systems decrypt those readings as soon as they reach a server or hub, so every intermediary can read them.

Partially homomorphic encryption offers another route. With the Paillier cryptosystem, an authorised service can add encrypted readings together and only the final total is ever decrypted. The catch is cost: Paillier operations are expensive, and smart homes generate frequent, small messages over constrained networks. My PhD focuses on **optimising partial homomorphic encryption for privacy-preserving smart-home IoT networks**, and on testing whether the resulting system still behaves correctly when it is attacked.

## My role

This is my doctoral project at the University of Huddersfield. I am responsible for the research design, building and integrating the virtual testbed, the Python implementation, running the experiments, analysing packet captures and logs, validating the data and writing up the results.

## The testbed

<Testbed />

The environment runs as five virtual machines on VirtualBox, each with one job:

- **Sensor publisher (Ubuntu).** Generates 15 simulated sensor streams, five sensor types with three instances each, at a nominal one reading per second in selected experiments.
- **MQTT broker.** Mosquitto, with authentication and topic access control, relaying messages between publishers and subscribers.
- **Authorised consumer.** Holds the private key, performs encrypted aggregation and decrypts only the totals it is authorised to see.
- **Home Assistant OS.** Receives decisions and drives automations. Later experiments linked processed sensor data to verified Home Assistant virtual-light actions.
- **Attacker machine.** An isolated environment used to run controlled replay, spoofing, flooding and malformed-message scenarios.

This is a research testbed with simulated sensors. It is not a commercial product or a deployment in real homes.

## Technical decisions

- **Paillier for additive aggregation.** Paillier is additively homomorphic: multiplying two ciphertexts produces a ciphertext of the sum. That fits aggregation of sensor readings, which is the operation smart-home analytics needs most often.
- **python-paillier with 2048 and 3072-bit keys.** Selected tests compare both key sizes so the cost of stronger keys is measured rather than assumed.
- **Integer encoding.** Sensor values are encoded as integers before encryption, and every encrypted result is checked against a plaintext reference.
- **Separate controls for integrity.** Paillier protects confidentiality but does not authenticate messages, and ciphertexts are malleable. My earlier experiments showed that replayed, injected and modified messages could still affect encrypted processing even when the Paillier arithmetic stayed correct. In the later Paper 5 prototype, the relay checks message age, duplicate message identifiers or payload hashes, sensor ticks and malformed messages, and replay and malformed-message defences passed controlled tests. Broker credentials and access control lists restrict unauthorised clients, but they do not prove that every message from an authorised publisher is genuine.

## Methodology

Each experiment is defined before it runs: the configuration, workload, duration, attack conditions and success criteria. Runs have stable identifiers so that figures, logs and captures can be traced back to the right experiment.

Evidence is collected at several points: packet captures with Wireshark and tcpdump, Mosquitto broker logs and application logs from the consumer and Home Assistant. Python scripts correlate these sources message by message.

Validation is independent of the code being tested: decryption checks against plaintext references, access-control tests, message accounting, SHA-256 integrity checks on archived evidence and separate audit scripts.

## What was measured

Across different experimental campaigns I measured message throughput, end-to-end latency, encryption and decryption time, and system behaviour in baseline, attack and encrypted-under-attack conditions. Different papers use different configurations and attack models, so their results are not combined into a single headline figure here. Figures will be added to this page from approved, published papers.

## Challenges and lessons

- Encrypted processing changes the timing of the whole system, not only the cryptographic step. Throughput and latency have to be measured end to end.
- A packet appearing in a capture does not prove the application processed it. Correlating several observation points was essential.
- Keeping experiments reproducible took as much engineering as building them: snapshots, configuration records, run identifiers and integrity hashes.
